# UNRELEASED

# 0.7.0

FEATURES

- Add `volume_name()` on `MountPoint` and `PathLocation`: the label a user sees beside a volume — `Macintosh HD`, `BACKUP`, `Untitled` — read from `NSURLVolumeNameKey` on Apple platforms, a `/dev/disk/by-label` reverse lookup on Linux (the identity's own udev road one directory across, with udev's `\x20`-style escapes decoded and the same refusal where two labels resolve to one device node), and `GetVolumeInformationW`'s volume name buffer on Windows. The BSDs publish no label reachable without a library or an ioctl this crate does not take, and report none.

  **A name is not an identity**, and the two are not interchangeable anywhere: a person can rewrite a label at any moment without the volume becoming another volume, two volumes may carry the same one, and a volume renamed while it was unmounted comes back under a name nothing recorded. `volume_identity()` stays the durable key and `volume_name()` is the caption; the name takes no part in `MountPoint`'s `PartialEq`, so a rename does not make a mount point a different mount point. Nothing caches a label either — a remembered one would age silently under exactly the rename it exists to show.

  Where the platform publishes no label, the documented **fallback** is the mount point's last path component (`usb` for `/media/alice/usb`), and the whole mount point where it has none — a filesystem root (`/`) and a Windows drive root (`C:`). The answer is never `Some("")`: a platform label that comes back empty is no label and falls back like any other, and `None` is left for the one case neither road can spell, bytes a `&str` cannot carry.

- Add `Display` for `VolumeIdentity`, the spelling the tools that read these values off a volume print: a UUID in its canonical `8-4-4-4-12` form, a FAT-class serial in the two dash-separated halves `blkid` and `diskutil` show, and a 64-bit serial as the sixteen hex digits printed for NTFS. Lowercase throughout, where some tools print the serials uppercase.

- **The CLI reports the volume, not just the path.** 0.6.0 gave the library a durable identity and left the `whichdisk` binary unable to print one; every resolve and every listing row now carries `volume_identity`, `identity_assurance`, `volume_name` and `is_ejectable`, in the plain output and in JSON and YAML alike. The three are renderings of one roster of fields rather than three hand-written copies of it, so every format names a field the same way and prints it in the same place; they differ only in how a value is spelled, a byte count being an exact number where a machine reads it and a human-readable size where a person does. A platform that reports no identity says so in the bare word `none` in the plain output, in `null` in JSON and in `~` — YAML's own null — in YAML, never in empty quotes, which would read as a volume whose identity is nothing. A text value in the plain output is quoted and escaped the way Rust spells a string, so that a label carrying a quote, a newline or a terminal control sequence cannot forge a field or a row. A law spawns the built binary and compares what it prints against the same question asked in-process, so the two cannot drift apart again.

- **A Linux mount source is a claim by whoever mounted it, and now says so.** `IdentityAssurance` gains a third level, `Declared`, below `Published`. The filesystem type in `/proc/self/mountinfo` is the kernel's own word, but the **source** beside it is a string the mounter supplied, and which of the two a read stands on is asked of the kernel itself: `/proc/filesystems` flags `nodev` every type mounted without backing storage. A type it does not so flag is one the kernel opens the source as a block device for, and what udev published about that device stands; a `nodev` type binds its source to nothing, and on a system allowing unprivileged user namespaces any user may mount `tmpfs` — or a plain `fuse`, or any `fuse.*` subtype — and name its source `/dev/sda1`. Both udev roads would then answer for that node about a filesystem that has nothing to do with it. The table is itself a source, and is taken from the kernel and from nowhere else. A path is not a name for a kernel table: a process may run in a mount namespace it does not own, and anything path-shaped in one can be interposed. `/proc` is therefore opened once and identified as procfs, and `filesystems` is reached from **that descriptor** under `RESOLVE_BENEATH`, `RESOLVE_NO_XDEV` and `RESOLVE_NO_SYMLINKS`, so a file bound over it — even one from procfs itself, a writable `comm` holding a line of the grammar — is `EXDEV` and a refusal. `openat2` is Linux 5.6 and later, and where it is missing this road fails closed rather than falling back to a path open that vouches for nothing. What comes back must be the exact grammar the kernel writes. A file that is not that table is refused whole rather than read for the lines that happen to parse, and a refused table vouches for nothing: every read through every mount source is then `Declared`. The static fallback serves one case only, the one where nothing is mounted there to read at all, and it names no `nodev` type, so it cannot grant what the rule exists to refuse.

  Asking the kernel is what makes this a roster of what *is* trustworthy rather than a list of what is known to be forgeable: a type nobody thought of, one loaded after this crate was written, and one whose name never reaches that table at all all fall to `Declared` rather than through the net. Such a read is **reported rather than refused**, at `Declared`, and the consumer decides: a caption shown to a person loses nothing by it, while anything minting or recognizing a volume by what it reads should take nothing at that level — `IdentityReading::is_declared()` is the one call that asks. Unlike `Published`, which names a window that closes on the next call, a declared source is a claim that stands as long as the mount does.

  The level covers **both halves**, because one mount source carries both: `MountPoint::volume_name_assurance()` and `PathLocation::volume_name_assurance()` report how a published label was read, and `None` where the fallback is naming the volume from its mount point rather than reading anything. The CLI prints it beside the name in all three output formats.

  A platform label is also reported **exactly as the platform published it**, and only where the platform published one a `&str` can carry: Windows read its UTF-16 label lossily, so a malformed one came back with replacement characters — a name the volume does not have, vouched for. It is read strictly now, and a label that does not decode is no published label, which leaves the mount point to name the volume. Apple and Windows trimmed the label before storing it, so a volume named ` BACKUP ` answered to `BACKUP` there and to ` BACKUP ` on Linux; trimming now decides only whether a label was published at all, and the bytes are reported as given.

  **Every kernel-owned table is read through a descriptor, never through a pathname.** A process may run in a mount namespace it does not own, and anything path-shaped in one can be interposed: a file bound over `/proc/filesystems`, a directory bound over `/dev/disk/by-label` holding a link of the mounter's choosing. Each root — `/proc`, `/dev`, `/sys` — is therefore opened once, and every entry under it is reached from *that* descriptor with `openat2` under `RESOLVE_BENEATH` and `RESOLVE_NO_XDEV`, so a mount interposed anywhere on the way is `EXDEV` and a refusal. The udev roads no longer compare paths at all: an entry under `/dev/disk/by-uuid` or `/dev/disk/by-label` is resolved to the **device number** the kernel names its target by, the mount source is resolved to one the same way, and the two numbers are compared — which retires `canonicalize()` from both roads and with it every question about where a symlink chain led. The btrfs census reads `fs/btrfs` beneath an authenticated `/sys`, addressing every entry from that root because a member under `devices/` is a symlink to the block device's own directory elsewhere in the tree — the one link the kernel puts there on purpose, and the one read that follows a link, still beneath the root and still across no mount. `/proc/self/mountinfo` comes from the same authenticated `/proc` as the filesystem table, under the number **that procfs** calls this process — read from the root's own `self` link and held to ASCII digits before any path is built from it, because a pid means something only in a pid namespace and the numeric directories of a procfs are named in the namespace it was mounted in, which need not be the caller's. A mount table that cannot be had that way is not had at all. The removable-device scan over `/dev/disk/by-id` takes the same guarded road, compares device numbers, and is **scanned once per operation and kept no longer** — a thread-lifetime answer to which devices udev calls removable is wrong the first time a disk is plugged in, and wrong again when a departed device's number is handed to another. Nothing kernel-derived is now cached across a call except the mount metadata the unique mount id witnesses. `openat2` being Linux 5.6 and later, a kernel without it fails every one of these roads closed; there is no static roster to fall back on, and none is needed, since a process that cannot reach the authenticated `/proc` resolves nothing at all.

  **A mount is chosen by identity, not by the length of its name.** `lookup_mountinfo` filtered only on the device number and then took the longest mount point among the candidates, so an unrelated bind mount sharing that number could supply the mount point, the source and the filesystem type — and, with the new fallback, the volume name. The mount id `statx` reports for the path is the id `mountinfo` prints in its first field, and where the kernel gives one it names exactly one line; otherwise the candidates are narrowed to the mounts whose mount point actually contains the path, compared on component boundaries, and the deepest of those wins.

  **What that does not do** is said in the code beside it, because it is less than it looks: a namespace the process does not own can present its own `/proc` and its own `/dev` wholesale, and `/proc/self/mountinfo` — where the filesystem type that decides `Declared` comes from — is equally theirs. The filesystem magic of a root says what *kind* of filesystem it is, never *whose*; `/dev` is not even asked, since what it carries is `tmpfs` or `ramfs`, which any user may mount. What these roads refuse is a bind interposed *under* a genuine root. That is worth refusing, and it is all that is claimed.

  **A btrfs label is read where every member can reach it.** `/dev/disk/by-label` holds one pathname per label, so a filesystem whose label another volume also carries is missing from it — and so is every member of a multi-device btrfs but the one udev happened to link. Mounted through any other member, the real label was missed and the mount point's last component silently stood in for it. This is the same one-link problem the identity road already takes the sysfs census to escape, so the label now takes it too: the kernel publishes it at `/sys/fs/btrfs/<fsid>/label`, beside the FSID, read beneath the authenticated `/sys` on the resolve road and the listing road alike and at the level the mount source earns. A census that refuses refuses the label with it, and the by-label road is not consulted in its place — a btrfs mount's identity is read from sysfs or not at all, and its label is read the same way and for the same reason.

  Where a label still cannot be read — two volumes sharing one label on any other filesystem — `volume_name()` falls back to the mount point's last component as documented, and `volume_name_assurance()` answers `None`, which is how a caller tells a label the platform published from a name this crate made up.

  The level a mount source earns is carried by **both** halves and by every road: the btrfs census in sysfs answers whether a device is a member of a filesystem, but the level that answer is reported at belongs to the mount source that named the device, so a refused filesystem table now leaves a btrfs identity `Declared` beside its `Declared` label rather than `Published` beside it.

- **`is_ejectable` was a lie of omission, and is now a three-state face.** `MountPoint::ejectability()` and `PathLocation::ejectability()` return an `Ejectability` — `Ejectable`, `NotEjectable`, or `Unknown` — because every road to this answer can fail, and a `bool` spelled all of those failures `false`: a denial the platform never made. **`NotEjectable` is answered only from an explicit platform answer to the removal question.** Every heuristic — a bus, a device name, a media flag, a drive type, an alias namespace — may produce `Ejectable` or `Unknown` and never a denial; `Unknown` is the default. **Apple** denies when both volume keys answer `false`. **Windows** denies when the device answers `IOCTL_STORAGE_GET_HOTPLUG_INFO` with no device hotplug and no removable or hot-pluggable media, or for a drive type that is not storage at all — and it now reads `DRIVE_CDROM` as ejectable and lets optical volumes through enumeration so they can be classified at all. **Linux never denies**: no unprivileged source there establishes that a drive is fixed — `removable` describes the media, a bus allowlist can only say yes, and a virtual device has no bus of its own — so it answers `Ejectable` (media `removable == 1`, a USB or MMC ancestry, or either of those on any device reached by walking `slaves/`, which is what carries a dm-crypt or LVM volume over an external disk) or `Unknown`. **The BSDs never deny**: a mount-table device name is not topology, so a name says yes only where its class is exclusively removable media — `cd`/`acd` and `fd` — and says nothing otherwise, `da` and `sd` and `ld` included.

  **The list filters carry the third state.** `ListOptions`' only-filters are exact: `ejectable_only` keeps exactly `Ejectable` and `non_ejectable_only` exactly `NotEjectable`, so a volume of unknown ejectability is excluded from both — it is not what either names. The CLI's `--skip-ejectable` and `--skip-non-ejectable` are the opposite question and no longer borrow those filters: each removes only its own named known state and keeps the unknowns.

  A negative is never derived from the absence of a positive, on any platform. Linux asks sysfs, keyed by the device number: `removable` reading `1`, or an ancestry through the USB or MMC subsystem, is `Ejectable` — the second is what catches the external USB disk whose own `removable` reads `0` — and only `removable` reading `0` *together with* neither ancestry is `NotEjectable`. Apple needs **both** volume keys to answer `false`; one `false` beside a silence is `Unknown`. Windows treats `DRIVE_CDROM` as ejectable and, where the drive type says `DRIVE_FIXED` — which is what it answers for an external USB disk — asks the device itself through `IOCTL_STORAGE_QUERY_PROPERTY`, whose `RemovableMedia` and `BusType` are the positive evidence; a query that cannot be made is `Unknown`. The BSDs report `Unknown` where `statfs` or `statvfs` failed. `is_ejectable()` remains as a convenience predicate meaning "the platform positively said yes", exactly as `IdentityReading::is_vouched()` sits beside `assurance()`, and the CLI prints `ejectability` as a word in all three formats where it printed `is_ejectable` as a boolean.

  A consumer that matches `IdentityAssurance` exhaustively will see the new variant and must add an arm, and one reading `is_ejectable` from the CLI's JSON or YAML must read `ejectability` instead.

- **A label no directory of one name per value can hold.** `/dev/disk/by-label` has one pathname per label, so the second volume to carry `NO NAME` — two USB sticks straight from the shop — has no link there at all. Where the authenticated roads have no answer, and only there, udev's own runtime database is consulted: it is keyed by the device number rather than by the label, so it answers where the directory cannot. **It is reported at `Declared`, never higher, whatever the mount source itself earned**, because it cannot be authenticated the way the other roots are: a label read from the udev runtime database is a claim by whoever controls `/run`, and on a system with unprivileged user namespaces that is not necessarily the system. It is reported, never vouched. The containment is the same regardless — opened beneath `/run` under `RESOLVE_BENEATH`, `RESOLVE_NO_XDEV` and `RESOLVE_NO_SYMLINKS`, read to a bound, parsed strictly, and `ID_FS_LABEL_ENC` rather than `ID_FS_LABEL`, since udev writes the latter with the characters it considers unsafe replaced by `_` and that is not the label the volume carries. btrfs never consults it: it has the sysfs census.

FIXES

- **One resolve, one mount.** `stat`, the cache witness, the mount id and the mount table were each sampled from the path independently, and a path is re-resolved on every call: a mount landing on top between two of those samples produced a device number from one mount and a witness from another, so the second mount's source and filesystem type were cached under the first mount's key behind a witness that still agreed — and later resolves of the first mount served the second's metadata for the life of the thread. Every one of those facts now comes off a single `O_PATH` descriptor that keeps naming the object the caller asked about.

  **The descriptor is held for the whole resolve**, not only long enough to read three numbers off it. A descriptor keeps a reference to the mount it is on, and the kernel returns a mount id to its allocator only when the mount is freed, so holding it is what stops that id from coming to name another mount between the `statx` that read it and the `/proc` read that uses it. Filesystem statistics are taken through it too, with `fstatvfs`: a `statvfs` by pathname re-resolves the mount point, which is how an overmount could supply another volume's capacity under this volume's source, identity and name. The listing road pins each row's mount point the same way and reports no capacity at all where the pinned mount is no longer the one the table named. And a row the kernel named by mount id is taken only while its mount point still contains the path — a mount table saying otherwise is no answer about that path, so nothing is returned rather than something. The device number is deliberately not that second gate: btrfs gives every subvolume its own anonymous number, so a path in a nested subvolume carries one the mount's own row never prints.

- **One resolve is one observation, and nothing is remembered.** The last mount cache — Linux's, keyed by `st_dev` and served while `statx`'s unique mount id agreed — is gone: that id names the mount *object*, not its attachment, and `do_move_mount` reattaches an existing mount without minting a new one, so an entry built at `/old` stayed vouched for after the mount moved to `/new`. No backend caches kernel state now, and there is no `thread_local!` left in the crate; the cost is one mount-table read per resolve, which every cache miss already paid. On Apple a resolve holds **one descriptor** for the whole call and asks `fstatfs` and `fgetattrlist` of it — the mount metadata, the capabilities, the identity **and the volume's label**, which is read with `ATTR_VOL_NAME` rather than through a pathname URL. The pin is best-effort by necessity, because a pathname `statfs` needs only search permission on the directories above an object while opening the object needs a right to the object itself; where the object cannot be opened for want of permission the mount root it reported is pinned instead and **verified against that same observation**, and where no verified descriptor can be had at all the row reports no identity and no label rather than values read from an independently resolved pathname. Every other open failure — descriptor exhaustion, an I/O error — is returned as the error it is. The other BSDs and NetBSD reach the same place by the opposite route: a single `statfs` or `statvfs` is the whole resolve, the ejectability now reading the device name that call already returned instead of making a second call of its own.

  **What this changes for a caller on Apple:** the two removal keys have no descriptor form, so they are fetched in one Foundation request *together with the volume's own UUID* and kept only where that UUID is the pinned volume's. On a modern macOS a URL for `/` resolves through the firmlinks to the **data** volume while `/` is the sealed system volume, so `resolve("/")` now reports `Ejectability::Unknown` where it used to report the data volume's answer as the system volume's. That was never this volume's answer to give. Every volume that is not firmlinked — which is every removable one, and every row of `list()`, whose keys come from the volume's own enumerated URL — answers exactly as before.

- **A mount cache no witness stood behind, on the BSDs and NetBSD.** Both backends kept the mount point, the mount source and the volume's capabilities in a thread-local entry keyed by `st_dev`. That key is not a witness: a device number names a mount session, the kernel hands it to another mount once the first goes away, and on Apple every volume of one APFS container shares one. A hit could therefore serve another volume's mount point — and the ejectability was asked of that mount point, which on Apple is a platform that *can* answer `NotEjectable`. A definitive denial obtained from a volume the caller never named is the worst answer this crate can give, so the entry is gone rather than refreshed: every field of a resolve is now what the kernel reports for that path at that moment, and every one of them is asked of the path the caller named. The cost is one `statfs` — one `statvfs` on NetBSD — per resolve, which a `disk-usage` build made on every call anyway.

- **A walk that could never run.** Linux reaches a stacked device's `slaves/` directory through `/sys/dev/block/<major>:<minor>`, which **is** a symlink: the number is an index, and the directory itself lives under `/sys/devices`. The structural opener refuses symlinks, so the open failed before `slaves` was ever read, and every dm-crypt, LVM or MD volume over removable storage answered `Unknown` no matter what was underneath it. A directory reached across a kernel-owned link now has its own opener, beside the one a file already had, still under `RESOLVE_BENEATH` and `RESOLVE_NO_XDEV`; the walk has laws over a fixture tree built with the links the kernel really publishes.

- **An Apple denial read from a lossy path.** The ejectability read built its `NSURL` from `to_string_lossy`, while the label read beside it had already moved to the path's filesystem representation. A path carrying bytes no `&str` carries becomes a *different* path that way — one that need not exist, and one that may sit on another volume — so two `false` answers about somewhere else could deny for the volume actually asked about. Both reads now go through one checked helper, and a path that cannot be represented is `Unknown`: not asked, rather than answered.

- **A disc mounted through its partition.** NetBSD and OpenBSD mount optical and floppy media as `/dev/cd0a` and `/dev/fd0a`, and the device-name matcher required every byte after the driver letters to be a digit — so the one class of drive these platforms can positively call removable was reported as unknown, and an exact ejectable listing dropped it. The matcher now reads a unit number followed by an optional disklabel partition letter, and still refuses a name that is not a device: `cdimages` and `cd0extra` say nothing, as before.

- **A listing no longer reads a device node's identity for a filesystem that merely named one.** `list()` on Linux canonicalized every mount source and looked the result up under `/dev/disk`, where a resolve first requires the source to be a device node. A filesystem is free to call itself whatever it likes — a FUSE mount may take `fsname=/tmp/link` pointing into `/dev`, and a bare name such as `overlay` canonicalizes against the process's own working directory — so a listed row could carry another volume's identity while resolving a path on that same mount reported none. Both udev roads, identity and label alike, now ask the one guard the resolve road asks, of the decoded source rather than of its escaped spelling.

# 0.6.0

FEATURES

- Add `VolumeIdentity`, exposing a volume's **durable identity** — the value stored on the volume itself, which survives unmounting, reboots, and moving the disk to another machine — via `volume_identity()` on `MountPoint` and `PathLocation`. It reports the raw platform fact rather than a composed string: `FsUuid` (a 128-bit filesystem UUID), `Serial64`, or `Serial32` (the weak FAT/exFAT class). Sourced per-OS — Apple `getattrlist` (`ATTR_VOL_UUID`), a `/dev/disk/by-uuid` reverse lookup on Linux, and `GetVolumeInformationW` plus `FSCTL_GET_NTFS_VOLUME_DATA` on Windows — and it honors the same `None`-means-nothing-to-report contract as `VolumeCapabilities`. The BSDs report `None`: their `f_fsid` is a mount-session handle handed out by `vfs_getnewfsid()`, not a property of the volume.

  **The answer says how it was read.** `volume_identity()` returns an `IdentityReading`: the `VolumeIdentity` together with the `IdentityAssurance` of the read that produced it. `Vouched` is a read of the mounted filesystem itself on this call — Apple's `getattrlist`, and Windows' calls addressed to the volume's own GUID path. `Published` is a name the platform published about a device, which is all Linux can offer unprivileged, and which can lag the media now behind that device for as long as udev takes to re-point its links. A consumer with something irreversible to do can require `Vouched` and treat `Published` as "not now"; one matching a volume it has seen before can take either. Nothing promotes one level to the other: settling a published name means reading the volume's superblock, which needs elevation this crate does not take. The assurance is not part of the identity — one disk read on two platforms gives one `VolumeIdentity` and two assurances, so it stays one registry key.

  The form is chosen **per filesystem**, so one volume answers with one identity wherever it is read: NTFS is the full 64-bit serial on both Linux and Windows, and an exFAT volume carrying no Volume GUID is the version-3 UUID Apple derives from its serial, computed identically on Linux and Windows from the serial they can read. Four narrowings cannot be avoided, and each is documented on the type rather than left to be discovered — an NTFS volume whose device Windows cannot open; a FAT12/16/32 volume on an Apple platform, whose UUID also takes a BPB sector count nothing else can reach; an exFAT volume carrying a native Volume GUID, which sits in the root directory and so needs elevation to read, and which Apple reports in place of the derived value; and an exFAT volume mounted through FUSE as bare `fuseblk`, a name that proves nothing about the format, whose serial is therefore reported as it stands (a FUSE mount that publishes `fuse.exfat` does prove it, and agrees with the kernel driver). Every one of them is a missed match, never a false one. A zero serial and the nil UUID are the absence of an identity on every platform, never a value.

  **No backend caches an identity.** Every platform reads it on every resolve, because no key available here can promise that the volume behind it is still the one an entry describes — a Unix `st_dev` names a mount session the kernel reuses, and a Windows volume GUID names durable *storage* while the serial is a value in the filesystem written onto it, which an offline tool rewrites without touching the GUID. What a mount-session key may still serve is the mount's own metadata, and only while a witness taken on that very resolve vouches for the entry: Linux carries the mount's unique id (`statx`, Linux 6.8+), serves an agreeing entry whole, and treats a disagreement and a kernel with no id to give alike, as a complete miss that re-reads `/proc/self/mountinfo`. Windows keeps nothing at all — one `GetVolumeInformationW` yields the capabilities and the serial together, so once the serial is read every time, an entry has no call left to save.

  A **btrfs** filesystem is reported by its FSID whichever of its devices carries the mount. Every member of a multi-device btrfs stores the same FSID, so `blkid` reads one name off all of them and udev can publish only one `/dev/disk/by-uuid` link for it; mounting by any other member left the filesystem with no identity at all. The kernel's own map — `/sys/fs/btrfs/<fsid>/devices/`, world-readable — is consulted first for btrfs mounts and matches the mount source's device number against the filesystem's members. Two narrowings sit beside that map, and both refuse rather than fall back to `/dev/disk/by-uuid` in their place: a **temporary FSID** — the runtime-only identity Linux 6.7+ mints for a clone mounted beside its on-disk original, marked by `<fsid>/temp_fsid` reading `1` — is not reported, since it does not survive to the next mount or the next machine; and a device number claimed by more than one filesystem — a **seed device**, shared read-only into several sprouts' `devices/` directories at once — is ambiguous, and none of the claimants is preferred over the rest. A sysfs read that fails partway through — an unreadable `devices/` directory, a member's unreadable `dev` file, a `temp_fsid` marker that exists but cannot be read — refuses the same way: the census is indeterminate, so no identity is reported from either road, and `/dev/disk/by-uuid` is never consulted in a refusal's place.

  Absence is never evidence, either. A mount `mountinfo` already reports as btrfs, whose sysfs census names no claimant at all — a readable-but-empty root, a bind mount that masks it, an FSID directory torn down between the `mountinfo` snapshot and this read — is refused rather than read as "not btrfs": the caller already knows otherwise, and a btrfs mount's identity is read from sysfs or not at all. A btrfs identity is reported only when the kernel positively states the FSID is permanent — `<fsid>/temp_fsid` reading exactly `0` on the matched candidate, an attribute present since Linux 6.7. Every other reading of that file — missing, unreadable, malformed, or `1` — refuses, regardless of a kernel-wide feature flag, another filesystem's own marker, or the running kernel's own release: earlier attempts inferred a missing marker's meaning from exactly those signals, and each one turned out spoofable or decoupled from what the running kernel actually ships (`uname(2)` is process-modifiable — the `UNAME26` personality reports a 2.6.x release on an arbitrarily new kernel — and a vendor backport of `temp_fsid` can just as easily ship it under a release numbered below 6.7). A kernel that predates Linux 6.7 and a masked or namespaced sysfs view on one that doesn't are indistinguishable from here, and both report no btrfs identity — a missed match, never a false one.

  On Linux the identity is as fresh as udev's links, and no fresher, which is what the `Published` assurance says: in the instant between new media appearing under a device node and udev re-pointing `/dev/disk/by-uuid`, the departed volume's name still resolves there. Nothing remembers that answer, so the window closes on the next call, and two checks narrow it further — a published name of a width the mount's own filesystem cannot carry is refused, and where two names resolve to one device node, neither is reported.

FIXES

- Fix a `list()` race on FreeBSD, OpenBSD, and DragonFlyBSD: two threads calling it at once could see `Err("Undefined error: 0")`, because `getmntinfo(3)` hands back a pointer into a process-wide buffer its own manual documents as reused and reallocated on every call, not a caller-owned one. The call and the copy-out of its entries are now serialized behind a lock, with the entries copied to owned memory before the lock is released. A `count <= 0` result with no errno set is now read as an empty mount list rather than turned into a fabricated error; a real errno still returns `Err`.

# 0.5.0
