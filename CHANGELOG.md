# UNRELEASED

# 0.7.0

FEATURES

- Add `volume_name()` on `MountPoint` and `PathLocation`: the label a user sees beside a volume — `Macintosh HD`, `BACKUP`, `Untitled` — read on Apple platforms with `getattrlist` `ATTR_VOL_NAME` through the descriptor a row is read through, in a resolve and a listing alike, a `/dev/disk/by-label` reverse lookup on Linux (the identity's own udev road one directory across, with udev's `\x20`-style escapes decoded and the same refusal where two labels resolve to one device node), and on Windows `FileFsVolumeInformation`'s label, through the one handle a row is read through. The BSDs publish no label reachable without a library or an ioctl this crate does not take, and report none.

  **A name is not an identity**, and the two are not interchangeable anywhere: a person can rewrite a label at any moment without the volume becoming another volume, two volumes may carry the same one, and a volume renamed while it was unmounted comes back under a name nothing recorded. `volume_identity()` stays the durable key and `volume_name()` is the caption; the name takes no part in `MountPoint`'s `PartialEq`, so a rename does not make a mount point a different mount point. Nothing caches a label either — a remembered one would age silently under exactly the rename it exists to show.

  Where the platform publishes no label, the documented **fallback** is the mount point's last path component (`usb` for `/media/alice/usb`), and the whole mount point where it has none — a filesystem root (`/`) and a Windows drive root (`C:`). The answer is never `Some("")`: a platform label that comes back empty is no label and falls back like any other, and `None` is left for the one case neither road can spell, bytes a `&str` cannot carry.

- Add `Display` for `VolumeIdentity`, the spelling the tools that read these values off a volume print: a UUID in its canonical `8-4-4-4-12` form, a FAT-class serial in the two dash-separated halves `blkid` and `diskutil` show, and a 64-bit serial as the sixteen hex digits printed for NTFS. Lowercase throughout, where some tools print the serials uppercase.

- **The CLI reports the volume, not just the path.** 0.6.0 gave the library a durable identity and left the `whichdisk` binary unable to print one; every resolve and every listing row now carries `volume_identity`, `identity_assurance`, `volume_name` and `is_ejectable`, in the plain output and in JSON and YAML alike. The three are renderings of one roster of fields rather than three hand-written copies of it, so every format names a field the same way and prints it in the same place; they differ only in how a value is spelled, a byte count being an exact number where a machine reads it and a human-readable size where a person does. A platform that reports no identity says so in the bare word `none` in the plain output, in `null` in JSON and in `~` — YAML's own null — in YAML, never in empty quotes, which would read as a volume whose identity is nothing. A text value in the plain output is quoted and escaped the way Rust spells a string, so that a label carrying a quote, a newline or a terminal control sequence cannot forge a field or a row. A law spawns the built binary and compares what it prints against the same question asked in-process, so the two cannot drift apart again.

- **A Linux mount source is a claim by whoever mounted it, and now says so.** `IdentityAssurance` gains a third level, `Declared`, below `Published`. The filesystem type in `/proc/self/mountinfo` is the kernel's own word, but the **source** beside it is a string the mounter supplied, and which of the two a read stands on is asked of the kernel itself: `/proc/filesystems` flags `nodev` every type mounted without backing storage. A type it does not so flag is one the kernel opens the source as a block device for, and what udev published about that device stands; a `nodev` type binds its source to nothing, and on a system allowing unprivileged user namespaces any user may mount `tmpfs` — or a plain `fuse`, or any `fuse.*` subtype — and name its source `/dev/sda1`. Both udev roads would then answer for that node about a filesystem that has nothing to do with it. The table is itself a source, and is taken from the kernel and from nowhere else. A path is not a name for a kernel table: a process may run in a mount namespace it does not own, and anything path-shaped in one can be interposed. `/proc` is therefore opened once and identified as procfs, and `filesystems` is reached from **that descriptor** under `RESOLVE_BENEATH`, `RESOLVE_NO_XDEV` and `RESOLVE_NO_SYMLINKS`, so a file bound over it — even one from procfs itself, a writable `comm` holding a line of the grammar — is `EXDEV` and a refusal. `openat2` is Linux 5.6 and later, and where it is missing this road fails closed rather than falling back to a path open that vouches for nothing. What comes back must be the exact grammar the kernel writes. A file that is not that table is refused whole rather than read for the lines that happen to parse, and a refused table vouches for nothing: every read through every mount source is then `Declared`. The static fallback serves one case only, the one where nothing is mounted there to read at all, and it names no `nodev` type, so it cannot grant what the rule exists to refuse.

  Asking the kernel is what makes this a roster of what *is* trustworthy rather than a list of what is known to be forgeable: a type nobody thought of, one loaded after this crate was written, and one whose name never reaches that table at all all fall to `Declared` rather than through the net. Such a read is **reported rather than refused**, at `Declared`, and the consumer decides: a caption shown to a person loses nothing by it, while anything minting or recognizing a volume by what it reads should take nothing at that level — `IdentityReading::is_declared()` is the one call that asks. Unlike `Published`, which names a window that closes on the next call, a declared source is a claim that stands as long as the mount does.

  The level covers **both halves**, because one mount source carries both: `MountPoint::volume_name_assurance()` and `PathLocation::volume_name_assurance()` report how a published label was read, and `None` where the fallback is naming the volume from its mount point rather than reading anything. The CLI prints it beside the name in all three output formats.

  A platform label is also reported **exactly as the platform published it**, and only where the platform published one a `&str` can carry: Windows read its UTF-16 label lossily, so a malformed one came back with replacement characters — a name the volume does not have, vouched for. It is read strictly now, and a label that does not decode is no published label, which leaves the mount point to name the volume. Apple and Windows trimmed the label before storing it, so a volume named ` BACKUP ` answered to `BACKUP` there and to ` BACKUP ` on Linux; trimming now decides only whether a label was published at all, and the bytes are reported as given.

  **Every kernel-owned table is read through a descriptor, never through a pathname.** A process may run in a mount namespace it does not own, and anything path-shaped in one can be interposed: a file bound over `/proc/filesystems`, a directory bound over `/dev/disk/by-label` holding a link of the mounter's choosing. Each root — `/proc`, `/dev`, `/sys` — is therefore opened once, and every entry under it is reached from *that* descriptor with `openat2` under `RESOLVE_BENEATH` and `RESOLVE_NO_XDEV`, so a mount interposed anywhere on the way is `EXDEV` and a refusal. The udev roads no longer compare paths at all: an entry under `/dev/disk/by-uuid` or `/dev/disk/by-label` is resolved to the **device number** the kernel names its target by, the mount source is resolved to one the same way, and the two numbers are compared — which retires `canonicalize()` from both roads and with it every question about where a symlink chain led. The btrfs census reads `fs/btrfs` beneath an authenticated `/sys`, addressing every entry from that root because a member under `devices/` is a symlink to the block device's own directory elsewhere in the tree — the one link the kernel puts there on purpose, and the one read that follows a link, still beneath the root and still across no mount. `/proc/self/mountinfo` comes from the same authenticated `/proc` as the filesystem table, under the number **that procfs** calls this process — read from the root's own `self` link and held to ASCII digits before any path is built from it, because a pid means something only in a pid namespace and the numeric directories of a procfs are named in the namespace it was mounted in, which need not be the caller's. A mount table that cannot be had that way is not had at all. The removable-device scan over `/dev/disk/by-id` takes the same guarded road, compares device numbers, and is **scanned once per operation and kept no longer** — a thread-lifetime answer to which devices udev calls removable is wrong the first time a disk is plugged in, and wrong again when a departed device's number is handed to another. Nothing kernel-derived is now cached across a call except the mount metadata the unique mount id witnesses. `openat2` being Linux 5.6 and later, a kernel without it fails every one of these roads closed; there is no static roster to fall back on, and none is needed, since a process that cannot reach the authenticated `/proc` resolves nothing at all.

  **A mount is chosen by identity, not by the length of its name.** `lookup_mountinfo` filtered only on the device number and then took the longest mount point among the candidates, so an unrelated bind mount sharing that number could supply the mount point, the source and the filesystem type — and, with the new fallback, the volume name. The mount id the pinned descriptor holds is the id `mountinfo` prints in its first field, and it names exactly one line: `statx` reports it, and where a kernel has no `STATX_MNT_ID` the descriptor's own `fdinfo` does. A kernel that names it through neither is refused rather than answered from a device number.

  **What that does not do** is said in the code beside it, because it is less than it looks: a namespace the process does not own can present its own `/proc` and its own `/dev` wholesale, and `/proc/self/mountinfo` — where the filesystem type that decides `Declared` comes from — is equally theirs. The filesystem magic of a root says what *kind* of filesystem it is, never *whose*; `/dev` is not even asked, since what it carries is `tmpfs` or `ramfs`, which any user may mount. What these roads refuse is a bind interposed *under* a genuine root. That is worth refusing, and it is all that is claimed.

  **A btrfs label is the filesystem's own answer.** `/dev/disk/by-label` holds one pathname per label, so a filesystem whose label another volume also carries is missing from it — and so is every member of a multi-device btrfs but the one udev happened to link. Mounted through any other member, the real label was missed and the mount point's last component silently stood in for it. The label is now asked of the filesystem itself, with `FS_IOC_GETFSLABEL` through the same descriptor its FSID is asked through (see *A btrfs mount binds through its own filesystem*), on the resolve road and the listing road alike and at the level the mount source earns. It does not wait on the mount's source resolving beneath `/dev`; a mount root this process may not open for reading has no label, and the by-label road is not consulted in its place.

  Where a label still cannot be read — two volumes sharing one label on any other filesystem — `volume_name()` falls back to the mount point's last component as documented, and `volume_name_assurance()` answers `None`, which is how a caller tells a label the platform published from a name this crate made up.

  The level a mount source earns is carried by **both** halves and by every road: the btrfs census in sysfs answers whether a device is a member of a filesystem, but the level that answer is reported at belongs to the mount source that named the device, so a refused filesystem table now leaves a btrfs identity `Declared` beside its `Declared` label rather than `Published` beside it.

- **`is_ejectable` was a lie of omission, and is now a three-state face.** `MountPoint::ejectability()` and `PathLocation::ejectability()` return an `Ejectability` — `Ejectable`, `NotEjectable`, or `Unknown` — because every road to this answer can fail, and a `bool` spelled all of those failures `false`: a denial the platform never made. **`NotEjectable` is answered only from an explicit platform answer to the removal question, bound to the mount the row holds.** Every heuristic — a bus, a device name, a media flag, a drive type, an alias namespace — may produce `Ejectable` or `Unknown` and never a denial; `Unknown` is the default, and every road that could not be asked leaves it. Each answer is bound by hold-and-verify: the device is read through the row's own descriptor or handle, the platform is asked, and the same descriptor or handle must still name that device afterwards, or the fact is dropped. **macOS** asks DiskArbitration about the device the pinned mount's own `fstatfs` names, where the kernel's `MNT_REMOVABLE` said nothing: a device inside the machine (`DADeviceInternal`) whose media neither ejects nor comes out is `NotEjectable` — the facts `diskutil info` prints as *Device Location* and *Removable Media* — and media that ejects or comes out, or a device outside the machine, is `Ejectable`. The description is bound by the device number the kernel wrote into the pinned mount's own filesystem id, never by a name or a path; the other Apple platforms have no DiskArbitration and never deny. **Windows** asks the Plug and Play removal policy of the disk the volume lies on: `EXPECT_NO_REMOVAL` is `NotEjectable`, and a policy that expects removal — orderly or surprise — is `Ejectable`; a Hyper-V machine's hot-pluggable virtual disk states that it expects removal, so on such a machine the boot volume answers `Ejectable`, as Windows itself offers to eject it. Where no policy is reached, the storage descriptor's bus (USB, SD) or media is the yes. The policy is Plug and Play's expectation for the disk's device node, so a Storage Spaces virtual disk or an iSCSI LUN whose node expects no removal answers `NotEjectable`, whatever storage lies behind it. **Linux** denies only where the kernel writes `fixed`: every USB device between the disk and its host controller reads `fixed` in the device core's `removable` attribute, no device on the way reads `removable` or `unknown`, and the disk's own media flag reads `0`. The kernel writes `fixed` for USB alone (a port the firmware describes as hard-wired, or a compound hub's non-removable port) and PCI writes only `removable`, so an internal SATA or NVMe disk stays `Unknown`. Every Linux removal answer, yes or no, is bound to the mounted filesystem and to one attach of the device rather than to its device number: the filesystem names itself through the mount (`FS_IOC_GETFSUUID` on Linux 6.9 and later, a FAT serial, btrfs's FSID), udev names the same identity for the device's current attach (`diskseq`, Linux 5.15, with its `by-diskseq` link, systemd 251), and every device the answer is read from keeps that attach — and every stack layer the members its `slaves/` lists, since the kernel changes no `diskseq` when a device mapper table is swapped or an md member replaced — until the answer is read. exFAT, NTFS, ISO 9660, UDF, and ext4 and XFS on a kernel before 6.9, therefore answer `Unknown`, and so does a device mapper or md device udev publishes no `by-diskseq` link for (systemd's rules give them none; lvm2's give device mapper devices one only in recent versions). For a filesystem that names no identity, udev's identity and label are read only for the attach `/dev/disk/by-diskseq` says udev published, where it names the device at all. **The BSDs never deny**: a mount-table device name is not topology, so a name says yes only where its class is exclusively removable media — `cd`/`acd` and `fd` — and only where the kernel's own filesystem type proves the kernel opened that device, and says nothing otherwise, `da` and `sd` and `ld` included. **`Ejectability` is `#[non_exhaustive]`**, so a later platform answer can have a word of its own; a match on it outside this crate needs a wildcard arm.

  **The list filters carry the third state.** `ListOptions`' only-filters are exact: `ejectable_only` keeps exactly `Ejectable` and `non_ejectable_only` exactly `NotEjectable`, so a volume of unknown ejectability is excluded from both — it is not what either names. The CLI's `--skip-ejectable` and `--skip-non-ejectable` are the opposite question and no longer borrow those filters: each removes only its own named known state and keeps the unknowns.

  A negative is never derived from the absence of a positive, on any platform. Linux asks sysfs, keyed by the device number: `removable` reading `1`, an ancestry through the USB subsystem that no `fixed` denied, a device on the way whose `removable` attribute reads `removable`, or an MMC card whose own `type` reads `SD`, is `Ejectable` — the USB ancestry is what catches the external USB disk whose own `removable` reads `0` — and only the explicit `fixed` above is `NotEjectable`. An MMC host carries soldered eMMC as often as a card slot, and the MMC block driver never sets `removable`, so an MMC ancestry alone is no answer: an eMMC is `Unknown`. Apple reads the kernel's own flag first, which can say yes and nothing else, and DiskArbitration's bound description where it says nothing. Windows reads the kind of device the file system reports (`FileFsDeviceInformation`) first: optical media and a removable medium are a yes. A disk whose medium is fixed in the drive — which is what an external USB disk is — is asked through its volume's own device (see *A Windows row is one handle's answer*): its disk's removal policy, and where none is reached its storage descriptor's bus. The BSDs report `Unknown` where `statfs` or `statvfs` failed. `is_ejectable()` remains as a convenience predicate meaning "the platform positively said yes", exactly as `IdentityReading::is_vouched()` sits beside `assurance()`, and the CLI prints `ejectability` as a word in all three formats where it printed `is_ejectable` as a boolean.

  A consumer that matches `IdentityAssurance` exhaustively will see the new variant and must add an arm, and one reading `is_ejectable` from the CLI's JSON or YAML must read `ejectability` instead.

- **A label no directory of one name per value can hold.** `/dev/disk/by-label` has one pathname per label, so the second volume to carry `NO NAME` — two USB sticks straight from the shop — has no link there at all. Where the authenticated roads have no answer, and only there, udev's own runtime database is consulted: it is keyed by the device number rather than by the label, so it answers where the directory cannot. **It is reported at `Declared`, never higher, whatever the mount source itself earned**, because it cannot be authenticated the way the other roots are: a label read from the udev runtime database is a claim by whoever controls `/run`, and on a system with unprivileged user namespaces that is not necessarily the system. It is reported, never vouched. The containment is the same regardless — opened beneath `/run` under `RESOLVE_BENEATH`, `RESOLVE_NO_XDEV` and `RESOLVE_NO_SYMLINKS`, read to a bound, parsed strictly, and `ID_FS_LABEL_ENC` rather than `ID_FS_LABEL`, since udev writes the latter with the characters it considers unsafe replaced by `_` and that is not the label the volume carries. btrfs never consults it: it has the sysfs census.

FIXES

- **One resolve, one mount.** `stat`, the cache witness, the mount id and the mount table were each sampled from the path independently, and a path is re-resolved on every call: a mount landing on top between two of those samples produced a device number from one mount and a witness from another, so the second mount's source and filesystem type were cached under the first mount's key behind a witness that still agreed — and later resolves of the first mount served the second's metadata for the life of the thread. Every one of those facts now comes off a single `O_PATH` descriptor that keeps naming the object the caller asked about.

  **The descriptor is held for the whole resolve**, not only long enough to read three numbers off it. A descriptor keeps a reference to the mount it is on, and the kernel returns a mount id to its allocator only when the mount is freed, so holding it is what stops that id from coming to name another mount between the `statx` that read it and the `/proc` read that uses it. Filesystem statistics are taken through it too, with `fstatvfs`: a `statvfs` by pathname re-resolves the mount point, which is how an overmount could supply another volume's capacity under this volume's source, identity and name. The listing road pins each row's mount point the same way and reports no capacity at all where the pinned mount is no longer the one the table named. And a row the kernel named by mount id is taken only while its mount point still contains the path — a mount table saying otherwise is no answer about that path, so nothing is returned rather than something. The device number is deliberately not that second gate: btrfs gives every subvolume its own anonymous number, so a path in a nested subvolume carries one the mount's own row never prints.

- **One resolve is one observation, and nothing is remembered.** The last mount cache — Linux's, keyed by `st_dev` and served while `statx`'s unique mount id agreed — is gone: that id names the mount *object*, not its attachment, and `do_move_mount` reattaches an existing mount without minting a new one, so an entry built at `/old` stayed vouched for after the mount moved to `/new`. No backend caches kernel state now, and there is no `thread_local!` left in the crate; the cost is one mount-table read per resolve, which every cache miss already paid. On Apple a resolve holds **one descriptor** for the whole call and asks `fstatfs` and `fgetattrlist` of it — the mount metadata, the capabilities, the identity **and the volume's label**, which is read with `ATTR_VOL_NAME` rather than through a pathname URL. The pin is best-effort by necessity, because a pathname `statfs` needs only search permission on the directories above an object while opening the object needs a right to the object itself; where the object cannot be opened for want of permission — `EACCES` or `EPERM` — that one pathname `statfs` is the whole row, and the row reports no identity, no label and nothing about removal rather than values read through anything else. No other descriptor stands in for the object's: opening the mount root instead would need a witness that the root and the path are on one live mount, and there is none — a mount point and a device are names, a volume UUID is shared by a clone and derived from a 32-bit serial on FAT and exFAT, and `st_dev`, `ATTR_CMN_DEVID` and `ATTR_CMN_FSID` are shared by the sealed system volume and its data volume. Every other open failure — descriptor exhaustion, an I/O error — is returned as the error it is. The other BSDs and NetBSD reach the same place by the opposite route: a single `statfs` or `statvfs` is the whole resolve, the ejectability now reading the device name that call already returned instead of making a second call of its own.

  **What this changes for a caller on Apple:** a resolve no longer asks Foundation's removal keys. They answer by pathname and have no descriptor form, and the only thing that could tie their answer back to the volume the resolve holds was that volume's UUID — which names a volume, not a mount, so a volume carrying the same UUID, mounted over the path for the length of the lookup, could answer for it. A resolve reads the kernel's own `MNT_REMOVABLE` flag instead, out of the same `fstatfs` its mount point and capacity come from: `Ejectable` where it is set, `Unknown` where it is not, and never `NotEjectable`. `resolve()` therefore reports `Unknown` for an internal volume where it used to report `NotEjectable`, and so does `list()` now: see *A listing row is one observation, as a resolve is*.

- **A mount cache no witness stood behind, on the BSDs and NetBSD.** Both backends kept the mount point, the mount source and the volume's capabilities in a thread-local entry keyed by `st_dev`. That key is not a witness: a device number names a mount session, the kernel hands it to another mount once the first goes away, and on Apple the sealed system volume and its data volume report one between them. A hit could therefore serve another volume's mount point — and the ejectability was asked of that mount point, which on Apple is a platform that *can* answer `NotEjectable`. A definitive denial obtained from a volume the caller never named is the worst answer this crate can give, so the entry is gone rather than refreshed: every field of a resolve is now what the kernel reports for that path at that moment, and every one of them is asked of the path the caller named. The cost is one `statfs` — one `statvfs` on NetBSD — per resolve, which a `disk-usage` build made on every call anyway.

- **A walk that could never run.** Linux reaches a stacked device's `slaves/` directory through `/sys/dev/block/<major>:<minor>`, which **is** a symlink: the number is an index, and the directory itself lives under `/sys/devices`. The structural opener refuses symlinks, so the open failed before `slaves` was ever read, and every dm-crypt, LVM or MD volume over removable storage answered `Unknown` no matter what was underneath it. A directory reached across a kernel-owned link now has its own opener, beside the one a file already had, still under `RESOLVE_BENEATH` and `RESOLVE_NO_XDEV`; the walk has laws over a fixture tree built with the links the kernel really publishes.

- **An Apple denial read from a lossy path.** The ejectability read built its `NSURL` from `to_string_lossy`, while the label read beside it had already moved to the path's filesystem representation. A path carrying bytes no `&str` carries becomes a *different* path that way — one that need not exist, and one that may sit on another volume — so two `false` answers about somewhere else could deny for the volume actually asked about. Both reads now go through one checked helper, and a path that cannot be represented is `Unknown`: not asked, rather than answered.

- **A listing row is one observation, as a resolve is.** The Apple listing took Foundation's name and removal keys from each enumerated URL, then read the mount metadata, the capabilities and the identity through three separate pathname lookups, so a volume replaced between any two of them left one row describing two mounts — a name and a definitive `NotEjectable` from one volume beside another's device and capacity. Each enumerated mount root is now pinned, and the row is built out of that one descriptor exactly as a resolve's is: its own `fstatfs` for the mount point, the source, the filesystem type, the capacity and the removal answer, and `fgetattrlist` through it for the capabilities, the identity and the label — `ATTR_VOL_NAME`, which answers what `NSURLVolumeNameKey` did. A row is reported only where that observation is of the mount the enumeration named and the mount says of itself that it is local and browsable; the enumeration is asked those two questions only so that a remote or hidden volume is never opened. **No Foundation key is a value in a row any more**, because nothing documents what binds a URL's answer to the mount a descriptor holds. That retires the removal keys — half an answer besides: `NSURLVolumeIsEjectableKey` and `NSURLVolumeIsRemovableKey` describe the media, and both say `false` for a USB disk — so the removal answer is the pinned mount's own `MNT_REMOVABLE` and, on macOS, DiskArbitration's description bound to the pinned mount (see the ejectability bullet above). A row is the one census entry its pin is: see *A listing row is bound by its mount's own witness*. The same rule binds the Linux listing's capacity: a row carries one only where a pin of its mount point holds the mount id the row was listed under while the mount table is read again, which a recycled device number cannot fake and which a btrfs subvolume's root — whose device number its own table line never prints — no longer misses; a row that cannot be held so is not reported at all — see *A row's facts are read only after its binding is proven*. A Windows row is read through one handle: see *A Windows row is one handle's answer*.

- **A failed read is not a volume with nothing to report.** On Apple platforms, Linux and Windows, a read the platform *declined* — the object is not there, the caller may not look, the containment refused the path, the question is not implemented — ends in that value's documented absence, and every other failure is returned as the error it is: an identity, a label, a mount table or a capacity is never reported absent because the descriptor table was full or a read hit an I/O error. Where a read used to be skipped rather than failed, the skip could change an answer: a udev directory entry passed over for failing to read may be exactly the second name for a device, which is the case the two-names-one-node refusal exists for, so a directory the platform stopped handing over partway is now no directory at all. A `statx` that failed took the weaker mount-table road, a mount table that could not be read came back as a `NotFound` that hid its real error, and an Apple listing dropped a volume whose `statfs` failed; each now keeps the error. Ejectability is the exception by its own definition — `Unknown` is the platform not having been asked. On Windows every road's absent and declined codes are listed in the backend's documentation beside the Microsoft page that names them, and a status an NT call returns is sorted as the system error it maps to.

- **An observation is formed once, from one native identity, and a row is built from nothing else.** Each platform has one observation type holding the pinned descriptor or handle together with the native identity it was pinned from; a row is built from that type alone, every field is read through it, and finding a path, a mount root or a volume GUID is private to its constructor. On Apple platforms the identity is a path's own filesystem bytes: the listing used to pin, and compare against the pinned `f_mntonname`, the `NSString` rendering of each enumerated URL, where encoding and normalization could make the pin miss a visible volume or land on another path that then passed the comparison; it now copies the URL's filesystem representation once and pins and compares exactly those bytes. A firmlinked path is split beneath its mount by the pinned descriptor's own `fcntl(F_GETPATH_NOFIRMLINK)` rather than by comparing a pathname `stat`'s device and file numbers with it — the system volume and its data volume share a device number — and a path that cannot be opened is not split beneath a mount point it does not begin with, since nothing binds another spelling of it to the object. On Linux the identity is the mount id the pinned descriptor holds: `statx`'s `STATX_MNT_ID`, else the `mnt_id:` line of the descriptor's own `fdinfo` (Linux 3.15), read beneath the authenticated `/proc` at the calling thread's own directory, else a named refusal. The old road for a kernel without `STATX_MNT_ID` chose the mount by `st_dev` against the table's `major:minor`, which a btrfs subvolume — whose anonymous device number its line never prints — could never pass, and which stacked mounts could pass for the wrong line. A listing row whose pin holds the id it was listed under is that id's line in the table read again while the pin is held, **wherever the mount is now**: a moved mount used to be dropped though its binding was sound.

- **A census ends where the platform proves it does.** Every directory the Linux backend reads — the two udev directories, the btrfs map in sysfs, a device's `slaves/` — goes through one reader over `getdents64`, and a census exists only once that call returned nothing. `rustix`'s `Dir`, which it used before, reads a refill that fails with `ENOENT` — a directory removed while it is being read — as the end of the directory, so a census could stop after one bufferful and report the prefix as the whole; a declined refill now refuses the census. The Windows volume enumeration is a census too: it ends only where `FindNextVolumeW` answers `ERROR_NO_MORE_FILES`, and any other failure of it fails the listing, where it used to end the enumeration quietly.

- **A Windows row is one handle's answer.** A resolve used to find its volume GUID path from the mount root, read the volume by that path, and then — where that first lookup failed — have its ejectability look the GUID up from the mount root a second time, so a transient failure followed by a drive-letter reassignment could put one volume's metadata beside another's removal answer. Now a resolve finds its path's mount root once and opens **one handle** on that root directory, and reads the volume GUID path through the handle (`GetFinalPathNameByHandleW`); a listing opens its handle through the GUID path the enumeration named, and asks for the volume's mount points while the handle holds it — and reports the volume only if it still answers for itself through the handle after that. Every field is read through the one handle: `NtQueryVolumeInformationFile` for the serial and label (`FileFsVolumeInformation`), the file-system name and flags (`FileFsAttributeInformation`), the capacity (`FileFsFullSizeInformation`) and the kind of device (`FileFsDeviceInformation`, where `GetDriveTypeW` used to be asked by name); `FSCTL_GET_NTFS_VOLUME_DATA` for the full NTFS serial. The handle is the root directory, opened for no access: a handle on the volume device itself, opened without read access — all an unelevated process is granted there — is a direct device open the file system never sees. **The removal question is the one fact asked through a second handle**: the volume's own device, opened only by the volume GUID path the one handle proved it holds — never by a path a caller gave, so it cannot land on another volume — and opened for no access, which a law proves an unprivileged process may do by opening it under a restricted token on every Windows runner. Through it are asked `IOCTL_STORAGE_GET_DEVICE_NUMBER`, which leads to the disk's Plug and Play removal policy, and `IOCTL_STORAGE_QUERY_PROPERTY`'s storage descriptor, whose USB or SD bus, or removable medium, is a yes where no policy answered. The disk's device node is reached by the one present disk interface carrying that device number, each interface opened for no access to be asked its own, and the number is read again through both handles after the policy was, so a disk that left in between drops the answer. A volume device this process may not open answers nothing, and the device kind's answer stands. `FILE_FS_VOLUME_INFORMATION`'s `SupportsObjects` is a `BOOLEAN` the binding crate types as a Rust `bool`, so every structure is read through an integer-only mirror a law holds to the binding's offsets. **What changes for a caller on Windows:** `NotEjectable` is the disk's own removal policy's answer, and `Ejectable` the policy's or the bus's (see the ejectability bullet above); a volume whose root cannot be opened — an empty card reader or optical drive, a volume with no file system — is not listed, where it used to be listed with no fields; a network share's device is its mount point, as before, and its fields come through the handle on its root; and a read that failed fails the call, where it used to report no identity, no label, no case flags or a zero capacity.

  The rule is now one type rather than a habit. Every platform read on Apple platforms and Linux answers one of four outcomes — a value, the platform's own "there is no such thing", a decline its backend names, or a failure — and none is taken for another except by a road that names what each means; there is no `ok()` to reach for. A census is read whole or refused: an entry of a udev directory whose link was declined while it was resolved used to be skipped as though it named no block device, so a partial census could report, at `Published`, a name the complete one would have withheld; it now refuses the whole directory. Only an entry that opened and is not a block device is passed over, and a name the road cannot read still counts as a name for its node. Foundation's errors are sorted to the same contract, where every one of them used to read as no value; an Apple capabilities read that failed is now the error it is rather than two unknown case flags. And the Linux removal question no longer fails a resolve or a listing: the `/sys` it is asked beneath was opened, and its failures returned, before the rule that every failure on that road is `Unknown` could apply — even for a mount whose source is no device at all. It is now opened only once a device is in hand, and whatever becomes of that open is `Unknown`.

- **No listing borrows storage the C library keeps.** FreeBSD, OpenBSD and DragonFly listed through `getmntinfo(3)`, which answers with a pointer into one buffer the C library keeps for the whole process and reallocates on the next call from anywhere in it. The lock this crate held around the copy serialised its own callers and nobody else's, so another library or the application calling `getmntinfo` during the copy could free the buffer under it — a data race and a use-after-free inside the safe `list()`. Every BSD-family listing — FreeBSD, OpenBSD, DragonFly, NetBSD and Apple platforms alike — now reads the kernel's mount table with `getfsstat(2)` (`getvfsstat(2)` on NetBSD) into a buffer the crate allocates for that one call. The Apple listing no longer asks Foundation to enumerate volumes: it reads the same table, reports a mount where the kernel's own flags call it local and browsable — the two questions it asked Foundation — and still pins each mount root and builds the row from that one descriptor. `objc2-foundation` is no longer a dependency.

- **A census is proven whole, or it is refused.** A table copied into a buffer the caller sized cannot say it was cut short: `getfsstat` and `getvfsstat` fill as many entries as the buffer holds and answer with that number when there were more, and NetBSD's listing sized its buffer to an earlier count, so a mount added in between was left out of a listing that read as complete. Every such table now goes through one reader that offers slots to spare, asks again with more room whenever an answer fills the buffer, and takes the census only from an answer that left a slot empty. The Linux mount table is read the same way in spirit: the kernel hands it over one `read(2)` at a time and keeps its place by position, so a mount added or removed between two pieces could skip a line, and a line that did not parse was passed over — both a mount left out of a table that read as complete. The table is now taken only from a read the kernel proves no mount event overlapped (`poll` answering no `POLLPRI` on the open file), and a line that does not parse fails the read. A Windows mount point that is not UTF-16 text used to be dropped from its volume's list while the rest stood for the whole; every string the Windows backend reads — a mount point, a volume GUID path, a file-system name — is now decoded whole or fails its read with `InvalidData`, and a label that is not text, on Windows and Apple platforms alike, is kept as the bytes the volume wrote, so `volume_name()` answers `None` for it and `volume_name_assurance()` still says a label was read, where the mount point used to be named instead.

- **A row is built from its observation and from nothing else, on every backend.** On Linux every fact of a row — the identity, the label, the removal answer and the capacity — is now read when the observation is formed, beneath roots its own constructor opens, and stored in it; the row is built from the observation alone. A btrfs mount's identity and label used to take a census of the kernel's btrfs map each, so a membership change between the two could pair one filesystem's FSID with another's label; one census now answers both. On Windows the observation owns its handle and the paths the volume is mounted at, and a row is built for each of those paths and nothing else; a listing's volume must also name itself, through its handle, by the GUID path its mount points were asked by, so mount points the mount manager gave for a name that moved to another volume are never paired with this one.

- **A disc mounted through its partition.** NetBSD and OpenBSD mount optical and floppy media as `/dev/cd0a` and `/dev/fd0a`, and the device-name matcher required every byte after the driver letters to be a digit — so the one class of drive these platforms can positively call removable was reported as unknown, and an exact ejectable listing dropped it. The matcher now reads a unit number followed by an optional disklabel partition letter, and still refuses a name that is not a device: `cdimages` and `cd0extra` say nothing, as before. The name is read only where the source is bound to the mount: see *A mount's source text is never a binding*.

- **A listing no longer reads a device node's identity for a filesystem that merely named one.** `list()` on Linux canonicalized every mount source and looked the result up under `/dev/disk`, where a resolve first requires the source to be a device node. A filesystem is free to call itself whatever it likes — a FUSE mount may take `fsname=/tmp/link` pointing into `/dev`, and a bare name such as `overlay` canonicalizes against the process's own working directory — so a listed row could carry another volume's identity while resolving a path on that same mount reported none. Both udev roads, identity and label alike, now ask the one guard the resolve road asks, of the decoded source rather than of its escaped spelling.

- **A row's facts are read only after its binding is proven, on every feature set.** A Linux listing built without `disk-usage` pinned nothing, and one built with it fell back to a row's first table line wherever the pin was missing or held another mount — and then read that line's device, identity, label and removal answer live, so a mount that had left, with its mount point or device node reused by another, came back as one row describing both. Every listing row is now pinned whatever the features, and a row is the line its pin's held id names in the table read again while the pins are held, or it is not reported: no fact is read about a line nothing proved. The mount table is read beneath the calling thread's own procfs directory (`thread-self`), where it was the thread-group leader's (`self`): a thread may enter a mount namespace of its own, and the pin and every pathname a row is read through resolve in the calling thread's. On Windows a resolve opened the mount root it had found by name and read whatever the open landed on; a volume mounted in a folder that left in between uncovered the folder, and the row paired the departed mount point with the host volume's facts. A handle is now accepted only where its own final path is exactly a volume GUID root — one typed parser, which every root the volume enumeration names goes through too — or, for a network share, which has no GUID path, exactly the share's root; anything else is declined, and nothing is read through it.

  What a Linux row's facts are read out of is read after that row is bound, too. The filesystem roster and the `/dev/disk/by-uuid` and `/dev/disk/by-label` censuses were read once for a whole listing, while its rows were pinned in batches of 64, so a row pinned in a later batch could take its identity or label from a census read before its pin; they are now read only once a table has been read while the rows' pins are held, one set per resolve and per batch, and dropped with it. **And a fact is read only about the device that backs the mount.** A mount source is a pathname the mounter supplied: the node a source names now binds only where it is the `major:minor` the kernel prints for the mount itself, and a source that does not bind has nothing read about it — no identity, no label, no removal answer. A node or link retargeted since the mount was made no longer lends the mount another device's facts, and a `tmpfs` or FUSE mount that names `/dev/sda1` as its source is no longer reported with that device's identity at `Declared`, nor as `Ejectable` because that device is: it is reported with neither. A btrfs mount carries an anonymous device the kernel prints in place of any member's, so its source binds only through the filesystem itself: see *A btrfs mount binds through its own filesystem*.

- **Every platform decoder is whole or `InvalidData` — never an absence, never a partial row.** The Linux mount table parser now holds every field of a record to the kernel's grammar — the parent id, the root, the per-mount and per-superblock options, the separator, every escape and the end of the record — and takes a record only at its newline, so a read cut short no longer yields a row (`21 x 8:1 garbage / rw - ext4 /dev/sda1` was one); `/proc/filesystems`, a descriptor's `fdinfo`, udev's runtime database, a sysfs `dev` file and a btrfs `label` are read the same way, and a bounded read that meets a file past its bound fails rather than handing its head over as the whole. A NetBSD census entry with an empty mount point or source used to be skipped, and a FreeBSD, OpenBSD, DragonFly or Apple entry whose string ran to the end of its array was read as far as the array went; every BSD-family entry is now decoded whole before any is weighed, and one that is not fails the call. DragonFly writes each mount point into the kernel's one shared copy of that mount's statistics on every `statfs` and `getfsstat` — cleared, then copied in — before copying it out, so a call that overlaps another anywhere on the system can be handed a mount point that is empty or cut short; there a resolve's `statfs` and a listing's census are taken only once the next answer agrees with them on every string, and a table that never settles is refused. NetBSD's census asks for the statistics the kernel keeps (`ST_NOWAIT`) rather than a refresh, because the kernel silently leaves out of a refreshing census every mount whose refresh fails; and it no longer asks for a count first, which the compatibility `getvfsstat` the `libc` crate links on NetBSD 10 and later never answers with the count: it hands the kernel a buffer of its own even for a count-only call. On Windows a structure short of its fixed part, a label or name length that is odd or runs past the answer, and a mount-point list that does not end exactly where its reported length does are `InvalidData`, where they were read as no label, no file-system type or a list closed by the buffer's own zeroes; and a volume that does not name its file system names no identity, so an NTFS volume's low half is never passed off as a whole 32-bit serial.

  The same rule reaches the decoders that still answered absence: a `thread-self` link that is not `<tgid>/task/<tid>`, an `fdinfo` file that does not end in a newline or whose `mnt_id:` line is not a tab and a decimal number, a `/proc/filesystems` that breaks the kernel's grammar (it read as an empty roster, which made every read `Declared`) and a btrfs `temp_fsid` that is neither `0` nor `1` (it let the row go on without its identity) are each `InvalidData`. udev's escapes are decoded strictly: its encoders write a backslash only as the start of `\xNN`, so a backslash that begins anything else, or an escape cut short, is `InvalidData` — in a `/dev/disk/by-label` name, which fails the census, and in the runtime database's `ID_FS_LABEL_ENC` alike — where it was kept as a byte of the label; and a database record is read whole before any key of it. A Windows volume label's length counts its trailing NUL where one is present, so that NUL is dropped and any other is `InvalidData`, and a file-system name of no length, or with a NUL in it, is `InvalidData`.

- **A kernel-filled buffer is read only within the length the kernel says it wrote.** Apple's `getattrlist` answers and Windows's volume queries and NTFS control code now fill a buffer that hands its decoders nothing but a view of the prefix the call reported writing, checked against the buffer before any field is read, so reading past it cannot be written. A volume name must begin in the answer's variable part, end inside what was written and carry exactly one terminating NUL; a capabilities or UUID answer must be exactly the length and the attribute asked for. The name buffer holds the longest name `getattrlist` documents, `NAME_MAX * 3 + 1` bytes, where a name longer than 255 bytes — a long non-ASCII HFS+ name — used to be reported as no label.

  A call that reports no length at all — `GetVolumePathNameW`, `FindFirstVolumeW`, `FindNextVolumeW`, Apple's `fcntl(F_GETPATH_NOFIRMLINK)` — marks the end of its answer only with the terminator it promises, and its buffer started zeroed, so an answer the call never finished could borrow one of the buffer's own zeroes as its end. Such a buffer now holds no zero whenever a call is handed it — every unit is a value that is no part of well-formed text, written again before each call and each retry — and its one reader ends the string at the first zero, which only the call can have written; none is `InvalidData`.

- **A btrfs mount binds through its own filesystem.** A btrfs mount's table line carries an anonymous device, so its source could bind to nothing, and every btrfs mount read no identity, no label and `Unknown` removal. The source now binds through the filesystem the pinned mount is. The mount point is pinned again (`O_PATH`, which triggers no automount) and taken only where that pin holds the observation's own mount id. It is reopened for reading through its own descriptor's magic link beneath the authenticated `/proc`, walking no path again, and held to the same mount id and to `BTRFS_SUPER_MAGIC`. It is asked `BTRFS_IOC_FS_INFO` for its FSID and `FS_IOC_GETFSLABEL` for its label, neither of which needs privilege. The identity is that FSID where `<fsid>/temp_fsid` says it outlives the mount, and the label is the filesystem's own, with or without a source that resolves beneath `/dev`; the source device, which the removal answer is asked about, binds only where the one census of `/sys/fs/btrfs` names exactly that FSID as the source node's one filesystem. A tmpfs or FUSE mount naming `/dev/sdX` never enters this road, so its source still binds nothing. A btrfs mount whose root this process may not open for reading, and a btrfs mount of a single file, bind nothing. A CI job mounts a real btrfs loop image and a subvolume of it beside it, and resolves and lists both.

- **A mount's source text is never a binding.** A mount's source, `f_mntfromname`, is text the mount call was handed: puffs(3) makes it a user-space server's own, and FUSE likewise, so a user-space filesystem could name `/dev/cd0a` and be reported `Ejectable` on FreeBSD, OpenBSD, DragonFly and NetBSD. A source is now read only where the kernel's own filesystem type proves the kernel opened the device it names, and the name is still a device node. The proving types are ones the kernel implements over a device it opens itself — `cd9660`, `udf`, `msdosfs`/`msdos`, `ufs`/`ffs`, `ext2fs` — which no user-space server can spell: theirs carry `fusefs`, `fuse` or the kernel-enforced `puffs|` prefix. On macOS the DiskArbitration description is bound the same way. The disk it describes must be the device the kernel wrote into the pinned mount's filesystem id (the first word of `f_fsid`, the device node's `st_rdev` for APFS and HFS). So a macFUSE mount stacked over a disk's mount point and naming that disk takes nothing from it.

- **A listing row is bound by its mount's own witness.** The Apple listing took a census entry for the mount its pin reached wherever the pinned mount's `f_mntonname` matched the entry's. Two mounts stacked at one path both passed: the mount on top was listed twice and the covered one never bound, and a volume that took a departed volume's path passed the same way. Each mount point is now pinned once, and the row is the one entry whose filesystem id (`f_fsid`), source, type and mount point are the pinned mount's own. A covered mount, a replaced one, and a pin that matches no entry or two are not reported.

- **A resolve never blocks on, or acts on, the object it names.** The pin the Apple resolve takes opened the caller's object for reading, so a FIFO waited for a writer — a resolve that never returned — and a Unix socket, which no open answers, failed the call, where the pathname `statfs` before it answered both. The object is now `stat`ed first, and only a regular file or a directory is ever opened, a directory only as one (`O_DIRECTORY`): a FIFO, a socket and a device node are described by their one `statfs` and never opened — opening a FIFO makes the caller one of its readers, and opening a serial device raises its DTR line — as a path this process may not open always was: no identity, no label, `Unknown` removal, and split beneath a firmlink by its parent directory's own `F_GETPATH_NOFIRMLINK`. The one window left is a regular file swapped for another kind between the `stat` and the open, which is opened non-blocking, with no controlling terminal, and let go unread. Both Apple pins take `O_NOFOLLOW`, and a row with no descriptor splits through the nearest directory above it that opens on its mount. On Windows, `canonicalize` opened and followed whatever a resolve was handed; a path that names a device — a DOS device name such as `NUL` or `COM1`, a raw drive or volume, a named pipe or mailslot, locally or through a host's `pipe`, `mailslot` or `IPC$` share, or the console's `CONIN$` and `CONOUT$` — is now refused with `InvalidInput` before anything is opened, decided on the string through `GetFullPathNameW`, which touches nothing, and every other path is walked one component at a time, relative to the handle on the one before, with no reparse point followed by the system: a symbolic link or a junction is followed only after its target is read through the handle that holds it and proven to be a drive's, a share's or a volume GUID's path, so a link to a named pipe or a serial port is refused, unopened, and a data reparse point is a file like any other. **What changes for a caller on Windows:** a path through a symbolic link or a junction on a network share, through a local link to a network path, through a name surrogate other than a symbolic link or a junction, or through a relative link that climbs above its root, is refused with `InvalidInput`; a path through a directory this process may not open for its attributes — one whose access list names the caller nowhere, which an open by full path passed through on the traverse privilege — fails with the access error, because the walk holds every directory it passes; a file under a third-party data reparse point no filter serves, which `canonicalize` could not open, now resolves. Linux pins with `O_PATH`, which opens no device, and the BSDs only ask `statfs` or `statvfs`.

- **A Windows resolve proves its root again after its facts are read.** The removal answer is asked through the volume's own device, opened by the GUID the root handle proved; the resolve now asks the root handle again, after every fact, whether it still holds that root, as a listing already did, and declines the volume where it does not.

- **A btrfs identity and label need no source beneath `/dev`.** Both are the filesystem's own answer through the pinned mount; the source binding now decides only the source device, which the removal answer is asked about, so a container whose `/dev` holds no disk nodes still reports a btrfs mount's identity and label.

- **A declared variable part ends the answer exactly.** Windows' `FileFsVolumeInformation` and `FileFsAttributeInformation` answers were read wherever their label or file-system name fit inside the length the file system reported, so bytes reported past it were ignored. MS-FSA has a successful answer end exactly at the fixed part and the string bytes it copied, and one that does not is now `InvalidData`. The same rule holds the storage descriptor to its own `Size`, and every other variable answer is read to exactly the length the call reported, or to the terminator it wrote.

# 0.6.0

FEATURES

- Add `VolumeIdentity`, exposing a volume's **durable identity** — the value stored on the volume itself, which survives unmounting, reboots, and moving the disk to another machine — via `volume_identity()` on `MountPoint` and `PathLocation`. It reports the raw platform fact rather than a composed string: `FsUuid` (a 128-bit filesystem UUID), `Serial64`, or `Serial32` (the weak FAT/exFAT class). Sourced per-OS — Apple `getattrlist` (`ATTR_VOL_UUID`), a `/dev/disk/by-uuid` reverse lookup on Linux, and `GetVolumeInformationW` plus `FSCTL_GET_NTFS_VOLUME_DATA` on Windows — and it honors the same `None`-means-nothing-to-report contract as `VolumeCapabilities`. The BSDs report `None`: their `f_fsid` is a mount-session handle handed out by `vfs_getnewfsid()`, not a property of the volume.

  **The answer says how it was read.** `volume_identity()` returns an `IdentityReading`: the `VolumeIdentity` together with the `IdentityAssurance` of the read that produced it. `Vouched` is a read of the mounted filesystem itself on this call — Apple's `getattrlist`, and Windows' calls addressed to the volume's own GUID path. `Published` is a name the platform published about a device, which is all Linux can offer unprivileged, and which can lag the media now behind that device for as long as udev takes to re-point its links. A consumer with something irreversible to do can require `Vouched` and treat `Published` as "not now"; one matching a volume it has seen before can take either. Nothing promotes one level to the other: settling a published name means reading the volume's superblock, which needs elevation this crate does not take. The assurance is not part of the identity — one disk read on two platforms gives one `VolumeIdentity` and two assurances, so it stays one registry key.

  The form is chosen **per filesystem**, so one volume answers with one identity wherever it is read: NTFS is the full 64-bit serial on both Linux and Windows, and an exFAT volume carrying no Volume GUID is the version-3 UUID Apple derives from its serial, computed identically on Linux and Windows from the serial they can read. Four narrowings cannot be avoided, and each is documented on the type rather than left to be discovered — an NTFS volume whose device Windows cannot open; a FAT12/16/32 volume on an Apple platform, whose UUID also takes a BPB sector count nothing else can reach; an exFAT volume carrying a native Volume GUID, which sits in the root directory and so needs elevation to read, and which Apple reports in place of the derived value; and an exFAT volume mounted through FUSE as bare `fuseblk`, a name that proves nothing about the format, whose serial is therefore reported as it stands (a FUSE mount that publishes `fuse.exfat` does prove it, and agrees with the kernel driver). Every one of them is a missed match, never a false one. A zero serial and the nil UUID are the absence of an identity on every platform, never a value.

  **No backend caches an identity.** Every platform reads it on every resolve, because no key available here can promise that the volume behind it is still the one an entry describes — a Unix `st_dev` names a mount session the kernel reuses, and a Windows volume GUID names durable *storage* while the serial is a value in the filesystem written onto it, which an offline tool rewrites without touching the GUID. What a mount-session key may still serve is the mount's own metadata, and only while a witness taken on that very resolve vouches for the entry: Linux carries the mount's unique id (`statx`, Linux 6.8+), serves an agreeing entry whole, and treats a disagreement and a kernel with no id to give alike, as a complete miss that re-reads `/proc/self/mountinfo`. Windows keeps nothing at all — one `GetVolumeInformationW` yields the capabilities and the serial together, so once the serial is read every time, an entry has no call left to save.

  A **btrfs** filesystem is reported by its FSID whichever of its devices carries the mount. Every member of a multi-device btrfs stores the same FSID, so `blkid` reads one name off all of them and udev can publish only one `/dev/disk/by-uuid` link for it; mounting by any other member left the filesystem with no identity at all. The kernel's own map — `/sys/fs/btrfs/<fsid>/devices/`, world-readable — matches the mount source's device number against the filesystem's members, and the FSID it names must be the one the mounted filesystem answers for itself through the pinned mount. Two narrowings sit beside that map, and both refuse rather than fall back to `/dev/disk/by-uuid` in their place: a **temporary FSID** — the runtime-only identity Linux 6.7+ mints for a clone mounted beside its on-disk original, marked by `<fsid>/temp_fsid` reading `1` — is not reported, since it does not survive to the next mount or the next machine; and a device number claimed by more than one filesystem — a **seed device**, shared read-only into several sprouts' `devices/` directories at once — is ambiguous, and none of the claimants is preferred over the rest. A sysfs read that fails partway through — an unreadable `devices/` directory, a member's unreadable `dev` file, a `temp_fsid` marker that exists but cannot be read — refuses the same way: the census is indeterminate, so no identity is reported from either road, and `/dev/disk/by-uuid` is never consulted in a refusal's place.

  Absence is never evidence, either. A mount `mountinfo` already reports as btrfs, whose sysfs census names no claimant at all — a readable-but-empty root, a bind mount that masks it, an FSID directory torn down between the `mountinfo` snapshot and this read — is refused rather than read as "not btrfs": the caller already knows otherwise, and a btrfs mount's identity is read from sysfs or not at all. A btrfs identity is reported only when the kernel positively states the FSID is permanent — `<fsid>/temp_fsid` reading exactly `0` on the matched candidate, an attribute present since Linux 6.7. Every other reading of that file — missing, unreadable, malformed, or `1` — refuses, regardless of a kernel-wide feature flag, another filesystem's own marker, or the running kernel's own release: earlier attempts inferred a missing marker's meaning from exactly those signals, and each one turned out spoofable or decoupled from what the running kernel actually ships (`uname(2)` is process-modifiable — the `UNAME26` personality reports a 2.6.x release on an arbitrarily new kernel — and a vendor backport of `temp_fsid` can just as easily ship it under a release numbered below 6.7). A kernel that predates Linux 6.7 and a masked or namespaced sysfs view on one that doesn't are indistinguishable from here, and both report no btrfs identity — a missed match, never a false one.

  On Linux the identity is as fresh as udev's links, and no fresher, which is what the `Published` assurance says: in the instant between new media appearing under a device node and udev re-pointing `/dev/disk/by-uuid`, the departed volume's name still resolves there. Nothing remembers that answer, so the window closes on the next call, and two checks narrow it further — a published name of a width the mount's own filesystem cannot carry is refused, and where two names resolve to one device node, neither is reported.

FIXES

- Fix a `list()` race on FreeBSD, OpenBSD, and DragonFlyBSD: two threads calling it at once could see `Err("Undefined error: 0")`, because `getmntinfo(3)` hands back a pointer into a process-wide buffer its own manual documents as reused and reallocated on every call, not a caller-owned one. The call and the copy-out of its entries are now serialized behind a lock, with the entries copied to owned memory before the lock is released. A `count <= 0` result with no errno set is now read as an empty mount list rather than turned into a fabricated error; a real errno still returns `Err`.
